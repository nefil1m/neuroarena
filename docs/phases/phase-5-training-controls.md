# Phase 5 — Training Controls

Status: **FINALIZED** — the requirements below are settled as of 2026-09-13; changing them needs a deliberate revision (see `../WORKFLOW.md`). Next is the Implementation plan section, then code.

## Goal
Configurable training/run behaviour: population size, simulation speed, success criteria, episode/generation timeouts, and the run-level and NEAT-internal controls a real training loop needs.

## Requirements
Settled through the 2026-09-13 Phase 5 exploration pass (carried over 2026-09-09 platform requirements, plus resolution of all four prior open questions and the cross-phase gaps a validation pass against Phase 4/Phase 6/Phase 7 found).

- **Config knobs:** population size; adjustable simulation speed; headless vs rendered; per-episode step limit (`CarEnvironmentConfig.max_episode_steps`, Phase 3); per-generation step ceiling (`RunConfig.max_generation_steps`, stubbed in Phase 4); track/map selection; sensor layout (Phase 3's `SensorConfig`); physics constants (Phase 1's `PhysicsConstants`); **run-level automatic stop** — a max-generations cap and a target-fitness threshold; **NEAT hyperparameters** — the full set `neat-python`'s config exposes (mutation rates, speciation compatibility threshold, crossover rate, and the rest), with defaults equal to the stock example config Phase 4 selected. "Inheritance between runs" is dropped from the knob set (see Revision history) — it named nothing beyond Phase 6's config-independent resume.
- **Track/map selection is live-changeable**, per `../OVERVIEW.md`'s user-driven track lifecycle (training continues on a track until the user regenerates or switches). Switching appends a settings-history entry (Phase 6) like any other live config change and does **not** start a fresh model: a track's geometry doesn't change the observation/action shape Phase 0's compatibility check compares (rays still return the same 7 proximity floats), only the underlying raycast distances — unlike a sensor-layout change (Phase 3), which does. **For NEAT (Phase 4), a switch takes effect at the next generation boundary**: recorded in the settings history immediately, but the population's per-genome environments don't move to the new track until the current generation's batch finishes, so every individual within one generation is compared on the same track.
- **Pluggable per-run success criteria** (e.g. finish line crossed / N checkpoints / one-lap completion vs. training indefinitely — the latter reads Phase 3's `lap_progress` and needs no new env-level mechanism, just an `Objective.should_stop()` that checks it). This governs when one *episode* ends; it is distinct from the new run-level automatic stop below, which governs when the whole *run* ends.
- **Run-level automatic stop** is new machinery, not a rewording of `Objective.should_stop()`: a run may end on its own once a max-generations cap and/or a target-fitness (best-so-far) threshold is reached, checked once per generation boundary alongside the existing per-generation ceiling check, in addition to the dashboard's (Phase 7) manual stop. Either knob is optional (unset = no automatic stop from that source); a run with neither set only stops manually, matching today's behaviour.
- **NEAT hyperparameters become configurable**, superseding no part of Phase 4's own decision: Phase 4 fixed the *default values* (the stock example config, "a documented starting point... real tuning happens once there's an actual training loop to observe and iterate against") and that default is unchanged here. Phase 5 only adds the capability to override those defaults per run via `RunConfig`, so a future tuning pass is a config change, not a doc revision. Exact field names and how they flow into `build_neat_config` are Implementation-plan-level detail (see Open questions).
- **Knob classification** — set-at-run-creation only (never live-changeable while a run is in progress) vs live-changeable:
  - **Set-at-run-creation only:** population size (resizing a live NEAT population mid-run has no well-defined semantics — which genomes are dropped/added, how speciation and the id allocators cope — and nothing in this project needs it yet; revisit with a deliberate revision if a real need arises), headless vs rendered, `Objective` selection (success-criteria choice), sensor layout (changing it mid-run breaks a running network's fixed input shape — per Phase 3, this always starts a fresh model, whether changed at creation or on resume).
  - **Live-changeable, effective at the next generation boundary** (same precedent as the existing track-switch rule, for the same reason — keeps every individual within one generation on a consistent comparison basis): track/map selection (already decided), physics constants (doesn't change the observation/action shape, so the general resume rule below already permits it — no new fresh-model rule needed), per-episode step limit, per-generation step ceiling, the max-generations cap, the target-fitness threshold, and the NEAT hyperparameter set.
  - **Live-changeable, effective immediately:** simulation speed (a rendering/pacing knob only; it touches no env or trainer state, so there is no generation-boundary consistency concern).
  - The dashboard (Phase 7) exposes the live-changeable subset.
- **Units:** the per-episode limit and per-generation ceiling are both step counts, matching what Phase 3 and Phase 4 already implemented (`CarEnvironmentConfig.max_episode_steps`, `RunConfig.max_generation_steps`) — not sim-time or wall-clock.
- **Settings are changeable between runs and on resume.** A model saved under one settings set can be resumed under a different (e.g. harder) set and continue training from its saved state — see Phase 6. This is valid as long as the observation and action descriptors are unchanged; changing sensor layout (Phase 3) starts a fresh model rather than a resume. Physics-constant changes fall under this same shape-based rule (see Knob classification above): they don't touch the observation/action descriptors, so they're always a valid resume, never a fresh-model trigger.

## Open questions
None remaining at the requirements level — see Revision history for how each item was resolved. Implementation-level details are left to the Implementation plan: the exact `RunConfig` field names for the two new run-level stop knobs and where `NeatTrainer.run()` checks them; the exact `neat-python` config parameters to expose and their `RunConfig` field names; and the mechanism for safely changing `neat.Config` hyperparameters between generations without corrupting `neat-python`'s internal state (id allocators, species bookkeeping) — the kind of state-corruption bug Phase 4's checkpoint-resume fix wave already found once in this same library, so this needs the same care.
