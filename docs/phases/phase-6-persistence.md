# Phase 6 — Persistence

Status: **FINALIZED** — the requirements below are settled as of 2026-09-13; changing them needs a deliberate revision (see `../WORKFLOW.md`). Next is the Implementation plan section, then code.

## Goal
Checkpointing, resume (including resume under changed settings), and run history — SQLite for metadata/history, files for checkpoints.

## Requirements
Settled through the 2026-09-13 Phase 6 exploration pass (carried over the 2026-09-09 platform requirements plus the 2026-09-10/2026-09-12 additions, plus resolution of all six prior open questions).

- **Storage split:** SQLite holds run metadata and history; model checkpoints are files.
- **Config-independent checkpoints:** a checkpoint holds the model state independent of the run configuration, so a model can be resumed under a different settings set and continue training from its saved state. Valid while the observation and action descriptors are unchanged; a sensor-layout change (Phase 3) starts a fresh model, not a resume.
- **Settings history per model:** a model carries an ordered log of every configuration change over its entire training lifetime — which settings changed, and the point in training (generation / step / wall-time) each change took effect.
- **Opening a model loads its most recent settings by default.** The user can then change them, which appends a new entry to the settings history.
- **Track/map reference, not track storage.** Maps are generated and stored as plain files by Phase 2 (`tracks/<track_id>.json` plus a manifest) — that storage is a **deliberate permanent design choice**, not a placeholder to migrate into SQLite later: tracks are static geometry artifacts, the same shape as checkpoints in the platform's existing "SQLite for metadata, files for artifacts" split (`../OVERVIEW.md`), not metrics that belong in a queryable table. Phase 6 does not re-store map contents; it adds a `track_id` column/reference to run metadata so "which map was this trained on" is answerable from SQLite alone, resolved to a file via Phase 2's manifest only when the map itself (not just its id) is needed. **Resolved:** Phase 2's plain-file manifest stays the only track index — SQLite never grows its own mirrored `tracks` table. No requirement has asked for SQL-side querying over track params, and a mirrored table would be a second source of truth that could drift from the manifest for a capability nothing needs yet.
- **Settings history per model includes track/map selection.** Track switching (Phase 5, live-changeable) is a config change like any other and appends a settings-history entry the same way population size or deviation limit would — no separate mechanism.
- **Run history is browsable from the dashboard** (Phase 9 for comparison views).
- **Per-generation stats log:** the `TrainingUpdate` stream a run emits (Phase 0) is persisted as the run's history — enough to redraw the fitness curve and compare generations by their stats without reloading a checkpoint.
- **Optional per-generation champion checkpoints** (config-gated, per Phase 4): the best genome/policy of a generation, stored so a chosen generation can be replayed later (Phase 9).

### Entity model: a model has many runs
A **model** is the persistent trainable artifact: it has an identity (`model_id`), a backend (`"neat"` for now; deep RL is Phase 10), the observation/action descriptors it was trained against, and the settings history and checkpoint lineage above. A **run** is one training session against a model — a fresh start or a resume — producing one contiguous segment of generation-stats. A model has many runs: resuming a model starts a new run row against the same `model_id`, rather than continuing the old run or creating a new model. This is what makes Phase 9's "cross-run comparison" and "model inspection... lineage" language coherent: a model's lineage *is* its ordered sequence of runs, and runs (not models) are the unit fitness curves are compared across. Generation numbering (`TrainingUpdate.progress_index`) is cumulative per model, continuing across a resume exactly as `NeatTrainer` already implements it — a run's `starting_generation` records where its segment began, not a per-run reset to zero.

### SQLite access: stdlib `sqlite3`, no ORM
Raw SQL behind a thin repository module per table (one save/load/list set of functions per entity, dataclasses in and out) — the same shape `tracks/store.py` already uses for track records, just backed by SQLite instead of one-JSON-file-per-record. Chosen over SQLAlchemy or a lighter ORM/helper (`sqlite-utils`, Peewee, SQLModel): this codebase's persistence code is consistently plain dataclasses plus explicit (de)serializer functions (`RunConfig`, NEAT checkpoints, track records) with zero ORMs anywhere, and a single-user local SQLite file doesn't need a query builder or session/identity-map machinery. Zero new production dependencies.

### Schema
Five tables, primary keys `uuid4().hex` strings (matching `track_id`'s existing convention, not autoincrement ints):
- **`models`** — `model_id`, `backend`, `observation_space` / `action_space` (JSON, informational — not the enforcement point; see Checkpoint format below), `created_at`.
- **`runs`** — `run_id`, `model_id` (FK), `track_id` (bare string reference into Phase 2's manifest — never resolved to a row), `started_at`, `ended_at`, `status` (`running` / `stopped` / `completed` / `crashed`), `starting_generation`.
- **`generation_stats`** — one row per `TrainingUpdate`: `model_id` (FK), `run_id` (FK), `generation` (= `progress_index`, cumulative per model), `best_fitness`, `mean_fitness`, `worst_fitness`, `population_size`, `champion_metrics` (JSON), `sim_time`, `wall_time`.
- **`settings_history`** — `model_id` (FK), `run_id` (FK), `generation` (the effective point), `changed_at`, `diff` (JSON of only the changed fields — not a full `RunConfig` snapshot; reconstructing "settings as of generation N" means replaying diffs forward from the model's first entry). Diff-only was chosen over a full snapshot per entry to avoid a model changed dozens of times over its life storing dozens of near-duplicate `RunConfig` blobs, matching this codebase's existing minimalism.
- **`checkpoints`** — `checkpoint_id`, `model_id` (FK), `run_id` (FK), `kind` (`resume` / `champion`), `generation`, `file_path`, `created_at`, `schema_version`. Both checkpoint kinds share one table (distinguished by `kind`) rather than two, so "every artifact for this model" is one query.

### Checkpoint format: opaque backend-owned file, SQLite holds only a reference
`NeatTrainer.save_checkpoint` / `load_checkpoint` (Phase 4, already implemented, tested, and FINALIZED) keep their exact pickle format, unchanged. Phase 6 does not define a shared checkpoint envelope that every backend's payload must conform to — it only adds the `checkpoints` table above, pointing at whatever file the backend wrote. This mirrors the track-storage precedent (SQLite/manifest references a file it does not parse) and avoids reopening Phase 4's finalized, tested checkpoint code for a uniformity requirement nothing has asked for; the same non-parsing relationship is how Phase 10's future deep-RL checkpoints slot in without a Phase 6 revision. File layout: `data/checkpoints/<model_id>/resume/gen_<N>.pkl` and `data/checkpoints/<model_id>/champion/gen_<N>.pkl`.

### Checkpoint cadence and retention
- **Resume checkpoints** (the full trainer-state pickle): saved every N generations (a new `RunConfig` knob, e.g. `checkpoint_every_n_generations`), and **every save is kept as its own file**, not overwritten — a run can be resumed from any past checkpoint, not only the most recent one.
- **Champion checkpoints** (one genome per generation, already implemented and config-gated via `NeatTrainer`'s existing `champion_dir` mechanism): **kept for every generation by default**, matching the stated goal that any generation can be re-simulated later. An optional retention cap (a new `RunConfig` knob, e.g. `champion_retention_cap`) is available to bound disk use on a long run — off (unbounded) by default, opt-in when it actually matters. Enforcing the cap (pruning older champion files/rows once the count exceeds it) is the persistence recorder's job (see below), not `NeatTrainer`'s — the trainer keeps unconditionally writing one champion per generation exactly as it does today.

### Launch entrypoint: `neuroarena-train` CLI
No phase has named a training-launch entrypoint yet — Phase 5's implementation plan explicitly left `RunConfig.track_id → Track`/`make_env` resolution and a `sim_speed`/`headless` consumer unbuilt for exactly this reason. Phase 6 needs to drive a real `Trainer.run()` loop end-to-end to exercise its own persistence machinery, so it closes this gap the same way Phase 2 closed the equivalent gap for track generation: a CLI dev tool (`neuroarena-train`, mirroring `neuroarena-track-gen`) now, with Phase 7's dashboard becoming a thin front end over the same underlying pieces later, no rework needed. The CLI resolves `track_id` into a `Track` (via Phase 2's `tracks/store.load`) and a `make_env` closure, builds the `Objective`/`Trainer`, creates the `models`/`runs` rows, and drives `run()` through a **persistence recorder**: a wrapper around the `TrainingUpdate` iterator that writes a `generation_stats` row per update, saves a resume checkpoint and inserts its `checkpoints` row every `checkpoint_every_n_generations`, applies the champion retention cap after each generation if set, and updates the `runs` row's `status`/`ended_at` when the loop ends (auto-stop, exhaustion, or an unhandled exception). A `--resume <model_id>` flag loads the latest `resume`-kind checkpoint for that model via `NeatTrainer.load_checkpoint` and starts a new `runs` row with `starting_generation` set from the restored state; a fresh run starts a new `models` row instead. Exact flag names are Implementation-plan-level detail.

### Minimal concrete `Objective`: `ProgressObjective`
Building `neuroarena-train` surfaced a cross-phase gap: Phase 0 assigned concrete `Objective` implementations to Phase 5 ("finish line crossed / N checkpoints / distance + speed shaping... Phase 5"), but Phase 5's implementation plan never built one — only a test double (`tests/interfaces/doubles.py`'s `DummyObjective`) exists anywhere in the codebase, unsuitable for a real training run. `neuroarena-train` cannot construct a `Trainer` without a real `Objective`, so Phase 6 adds exactly one: `ProgressObjective`, reading the car env's existing `info` fields (Phase 3's `progress` / `lap_progress` / `crashed`) — `fitness()` returns cumulative `progress`, `step_reward()` returns the per-step `progress` delta, `should_stop()` is true once `lap_progress >= 1.0`. This is necessary infrastructure to make the CLI runnable, not a reopening of Phase 5's "pluggable success criteria" requirement: selecting *between* multiple objectives (finish line vs. N checkpoints vs. this one) stays unbuilt, deferred to whichever phase adds objective-selection UI (Phase 5's Requirements already classify `Objective` selection as set-at-run-creation-only, i.e. a Phase 7 dashboard concern). Lives in `neuroarena/sim/` (car-specific, unlike the game-agnostic interfaces) alongside `car_env.py`.

### Schema versioning
The SQLite schema itself is versioned and forward-migrated the same way every other persisted format in this codebase already is (`RunConfig.schema_version`, the NEAT checkpoint's `schema_version`, `TrackRecord`'s `schema_version`): a single version number (`PRAGMA user_version` or a one-row `meta` table) plus ordered `.sql` migration files applied in sequence at startup, rather than a new pattern invented for this one subsystem.

## Open questions
None remaining at the requirements level — see Revision history for how each of the six prior open questions was resolved. Implementation-level details are left to the Implementation plan: exact table/column names and SQL DDL, the `neuroarena-train` CLI's flag names, the exact `RunConfig` field names for `checkpoint_every_n_generations` and `champion_retention_cap`, the migration-runner mechanics, and how the persistence recorder's champion-retention pruning identifies "oldest" (generation order, since champion files are already named `gen_<N>.pkl`).

## Implementation plan
Detailed, step-by-step plan: [`../superpowers/plans/2026-09-13-phase-6-persistence.md`](../superpowers/plans/2026-09-13-phase-6-persistence.md).

Eleven tasks, each ending in an independently testable, committed deliverable:
1. **Migration-driven SQLite connection** (`persistence/db.py`) — `PRAGMA user_version` + ordered `.sql` migrations, the initial 5-table schema.
2. **`models` repository** + a `Space` (`Box`/`Discrete`) JSON codec.
3. **`runs` repository** — the model-has-many-runs entity.
4. **`generation_stats` repository** — one row per `TrainingUpdate`.
5. **`checkpoints` repository** — metadata only, references an opaque backend-owned file.
6. **Two new `RunConfig` knobs** — `checkpoint_every_n_generations`, `champion_retention_cap`.
7. **`settings_history` repository** — diff-only entries, `compute_diff`/`reconstruct_run_config`.
8. **`ProgressObjective`** (`sim/objectives.py`) — the first concrete `Objective` in this codebase.
9. **Persistence recorder** (`persistence/recorder.py`) — wraps any `Trainer.run()` iterator; backend-agnostic.
10. **`neuroarena-train` CLI** — the first working training-launch entrypoint, fresh-start and `--resume`.
11. **Whole-suite verification** — full suite, `ruff`, `mypy --strict`, and a re-confirmation of Phase 4's NEAT import-hygiene guard.

All were fixed in one consolidated fix wave (this process allows exactly one) and independently re-verified by a scoped re-review that re-derived the hardest properties itself rather than trusting the fix report (a spy on `NeatTrainer.load_checkpoint`'s actual call, an end-to-end fresh-then-resume run, and a hand-trace of the checkpoint generation-counter arithmetic):
    - **Critical, now fixed:** `--resume` originally built its `RunConfig` purely from CLI-argument defaults rather than seeding from the model's actual last-known settings (`settings_history_repo.reconstruct_run_config`) — an unpassed flag silently reverted that knob, violating this doc's own "opening a model loads its most recent settings by default" requirement, and recorded a `settings_history` diff for a change that never took effect (`NeatTrainer.load_checkpoint` always keeps the checkpoint's own population size regardless of what config is passed). Fixed: every resume-relevant CLI knob defaults to "unspecified" rather than a concrete value, unspecified knobs inherit the model's reconstructed settings, and an explicit `--population-size` that would actually change the population on resume is refused with a clear error rather than silently accepted or silently ignored.
    - **Important, now fixed:** a `KeyboardInterrupt` (the normal way a headless CLI run ends) left a `runs` row stuck at `status="running"` forever — `except Exception` doesn't catch it, since `KeyboardInterrupt` is a `BaseException`. Now sets the reserved `"stopped"` status. `run_and_record`'s returned `RunRecord` was stale (always showed `"running"` even after the DB was updated to `"completed"`) — now returns the post-update record. Champion-checkpoint retention pruning could delete a file a surviving (duplicate, from a replayed resume) row still referenced — now checks for a shared `file_path` among survivors before unlinking. `ORDER BY generation` had no tiebreaker in three repositories, letting same-generation ties (reachable via a resume that replays already-recorded generations) sort in SQLite's arbitrary order and silently corrupt `reconstruct_run_config`'s replay — now `ORDER BY generation, id` (or `, created_at` for `checkpoints`, which has no autoincrement id). `runs.starting_generation` was off by one on resume (recorded the last generation of the *previous* segment instead of where the new one begins) — now `latest.generation + 1`, matching `NeatTrainer`'s own pre/post-increment counter semantics. `--checkpoint-every-n-generations 0` crashed mid-run with a `ZeroDivisionError` after DB rows already existed — now validated before any write. `neuroarena-train`'s `main()` had no error handling, so every deliberate, clear error surfaced as a raw traceback — now routed through a clean usage-style message.

This is strictly correct (and strictly better than the pre-fix behavior, which inherited nothing and would have trained forever) but is a real UX surprise for the obvious `neuroarena-train --track-id X --resume Y` invocation with no other flags — worth a line in the CLI's own `--help` text or a dashboard-level affordance when Phase 7 builds one, not a Phase 6 code change.
