# Phase 1 — Playable Game Core

Status: **FINALIZED** — the requirements below are settled as of 2026-09-12; changing them needs a deliberate revision (see `../WORKFLOW.md`). Next is the Implementation plan section, then code.

## Goal
Kinematic car with manual control on one static track, drawn by a sprite-based renderer.

## Requirements
Settled through the 2026-09-12 Phase 1 exploration pass (grounded in an actual tile-based racing art kit).

- **Car physics — kinematic bicycle model:** state is `(x, y, heading, speed)`. Controls are continuous: `steering ∈ [−1, 1]` and `throttle ∈ [−1, 1]`. No tire slip / drift in v1 (a dynamic model can slot in later behind the same interface). **Throttle semantics — brake first, then reverse:** while moving forward, negative throttle decelerates; only once speed reaches ~0 does continued negative throttle accelerate backward. **Constants** (world units — see world-scale below; explicitly tunable, not fixed law; tuned once already after play-testing, see Revision history): `wheelbase = 180`, `max_steering_angle = 35°`, `max_speed = 750 units/s` (forward), `accel = 375 units/s²`, `brake_decel = 750 units/s²`, `max_reverse_speed = 300 units/s`, `reverse_accel = 225 units/s²`, `wall_friction = 0.15` (fraction of into-wall speed lost on a boundary hit — the boundary is a hard collider either way, this only tunes how punishing hitting it feels; kept low for human play so a graze doesn't leave the car crawling, per Revision history).
- **World scale:** `cell_size = 512` world units, equal to a road tile's native pixel size (`Road_Main` is already an exact tileable 512×512 square, so tiles need no rescaling). The car sprite is **not** taken at native pixel size or at its original drivable-width-derived scale — its native dimensions (565×1146px) don't fit the drivable width (a straight tile's drivable width is `512 − 2×93(kerb strips) = 326` units) at 1:1, and the first drivable-width-derived scale (`car_width ≈ 148` / `car_length ≈ 300`) played too large once actually driven. Sized down to `car_width ≈ 49` / `car_length = 100` world units after play-testing (preserving the sprite's aspect ratio) — each asset category still gets its own explicit render scale rather than one shared native-pixel-equals-world-unit rule; only the car's scale factor changed.
- **Tick rate — fixed physics step, decoupled from playback speed:** the simulation always advances in a fixed timestep (`TICK_DT = 1/60s`), which is what makes the "deterministic given seed + genome" replay guarantee (`../OVERVIEW.md`) hold reliably. Phase 5's adjustable simulation speed changes only how many fixed ticks run per real second (wall-clock pacing) — headless training is unpaced and runs as fast as the CPU allows; the physics step size itself never changes.
- **One hand-authored static track** for this phase; procedural generation is Phase 2. The track is defined by collision geometry (a drivable region plus its boundary). Leaving the boundary is "off track"; boundary collision is always on. **In Phase 1, "always on" means a hard physical collider at the boundary** — the car cannot cross it (stop/bounce), independent of and prior to Phase 3's `terminated`-on-off-track wiring. This is a deliberate Phase 1 choice, not yet the general policy: Phase 3 may still express off-track detection differently for training (e.g. detecting the crossing rather than physically blocking it), since a hard wall could mask a genome's true trajectory.
- **Track representation — a closed-loop path on a grid, 90° turns only:** a track is an ordered, closed sequence of grid cells, each tagged with a `TileKind` (`STRAIGHT_NS`, `STRAIGHT_EW`, `CURVE_NE`, `CURVE_NW`, `CURVE_SE`, `CURVE_SW` — a `CURVE_XY` connects that cell's `X`-facing and `Y`-facing edges) and a shared `cell_size` world-unit constant. Collision geometry (the drivable corridor + boundary) and the renderable tile sequence are both derived from this one path — there is no separate freeform geometry model. Phase 2 generates the same representation (a sequence of grid moves that closes into a loop) rather than a different one; it does not need to reopen this decision. One cell is designated `start_cell` (+ `facing ∈ {N, E, S, W}`): it is both the car's spawn point and the lap line, since tracks are closed loops (see Revision history). **File format:** JSON with a top-level integer `schema_version`, mirroring the Phase 0 `RunConfig` codec convention — one serialization pattern project-wide.
- **Tile art — a uniform surface fill, resolved by a per-style asset manifest, plus procedurally-drawn kerbs:** every cell is filled with one undirected, edge-to-edge asphalt texture from the manifest (no per-`TileKind` art, no rotation) — the same texture regardless of `TileKind`, since the manifest previously tried to back each `TileKind` with its own oriented composite/layer art and that broke twice over (non-square canvases left visible seams once rotated, and a manual per-`TileKind` rotation-degrees mapping put several corners' kerbs on the wrong edges). Kerb lines are instead drawn directly from `boundary_segments` — the same collision-boundary geometry the collider already enforces — so the visible kerb and the collidable wall can't disagree, and adding a style only means swapping the fill texture, not re-deriving a rotation table. Swapping road styles (or a placeholder style) still means swapping the manifest, not the renderer. See Revision history for the two-bug story behind this.
- **Decor overlay, independent of the tile grid:** start/finish markers and scenery (trees, rocks, buildings, …) are placements — `(world position, heading, texture, z-order)` — layered on top of the tile grid, non-collidable, and not part of the track's collision geometry. The `start_cell` above drives where the start/finish decal is placed; concrete decor items beyond that are free to grow without touching track or collision data.
- **Renderer built on the `arcade` library**, living only in the render layer and reading simulation state. It is swappable and never required for the sim to run. Pygame is the documented fallback (e.g. if WSL2 OpenGL proves unreliable).
- **It must look like a real game:** a car sprite continuously rotated to match heading (a single texture, not a preset-angle frame set), a road surface, kerbs, scenery, and a camera that follows the car. Real art assets are already available (a tile-based racing kit); placeholder art is the fallback only where a given slot's real asset isn't ready yet, not the default. Collision geometry and visual assets are separate layers.
- **Human-playable:** a keyboard/gamepad input adapter produces the same `(steering, throttle)` output a model does — a human is just another policy. This is a permanent feature, not a bootstrapping throwaway.

## Open questions
None remaining at the requirements level — see Revision history for how each prior open question (track/asset representation, boundary-collision behavior, file format, physics constants, world scale, tick rate) was resolved. Genuinely implementation-level details (e.g. camera follow easing/zoom, exact key/gamepad bindings) are left to the Implementation plan rather than tracked here.

Note: damage-state car frames exist in the available art (alternate sprites, not steering/rotation frames) but are out of scope for Phase 1 — reserved as a possible later decor/state slot, not a requirement here.

## Implementation plan
Detailed, step-by-step plan: [`../superpowers/plans/2026-09-12-phase-1-game-core.md`](../superpowers/plans/2026-09-12-phase-1-game-core.md).

Seven tasks, each ending in an independently testable, committed deliverable:
1. **Track representation** — `TileKind`, `Track`, closed-loop validation, boundary-segment derivation, JSON `schema_version` codec, one hand-authored track fixture.
2. **Car physics** — kinematic bicycle model, brake-first-then-reverse throttle, the doc's starting constants.
3. **Collision** — hard boundary collider (stop, not bounce; tangential velocity survives a graze).
4. **Game loop** — `Game.tick(steering, throttle)` at fixed `TICK_DT`, spawns at `start_cell`/`start_facing`.
5. **Asset manifest loader** — resolves each `TileKind` to composite-or-layered textures plus rotation metadata, validates files exist.
6. **Renderer (`arcade`)** — tile/decor/car drawing, camera follow, fixed-step accumulator decoupled from display framerate.
7. **Input adapter + play entry point** — keyboard → `(steering, throttle)`, `uv run neuroarena-play`.

`sim` stays free of `arcade`/`gymnasium`/episode concepts throughout (enforced by an import-hygiene test, mirroring Phase 0's); `render` imports `sim`, never the reverse.

Four implementation-level findings surfaced while building, none changing a Requirement: (1) **Collision uses a bounding-circle approximation of the car body** (radius = half the car's width), not a full oriented rectangle — simpler and robust against tunneling at this tick rate/speed range; documented in `collision.py`. (2) **The asset manifest prefers each tile's composite image over its layer stack**, reversing the plan's stated default — the vendored kit's layer exports are cropped to each layer's own content with no shared-canvas offset metadata (e.g. the curve tile's `Road_Side_02` layer is a 96×96 drain-cover icon, not a full-tile image), so compositing them without that missing offset data would misplace them; the composite is already correctly flattened. Layers stay resolvable in the manifest for whenever offset metadata is added. (3) **Tile sprites are scaled by width only, preserving the art's native aspect ratio**, not forced to a `cell_size × cell_size` square — the vendored composites aren't all exactly square (the straight tile's is 512×688), and forcing one would visibly squash it. (4) **Sprite-to-heading rotation math was derived empirically**, not assumed: rendered the car and decor art at several angles and inspected the output to find each texture's native facing before writing the world-heading-to-sprite-angle conversion (`arcade.Sprite.angle` turned out to rotate clockwise from the texture's unrotated orientation). Known cosmetic wrinkle, not a bug: the single start/finish banner asset reads correctly only for a north/south-facing start line — this fixture's east-facing start renders the checker band correctly (perpendicular to travel) but its "START" text sideways, an inherent limit of using one rigid banner texture for both track orientations; not worth a second asset slot for Phase 1.
- 2026-09-12 — Manual play-testing (the first actual interactive run, as opposed to headless screenshot review) surfaced two bugs the screenshots had missed, plus one the screenshots *had* shown but I'd misjudged: the car drove tail-first (the heading→sprite-angle offset derived in the previous entry was 180° backwards — fixed once the user watched it actually drive), and every curve corner's kerb sat on the wrong edges (the manual per-`TileKind` rotation-degrees mapping used to orient the base curve art was backwards). Rather than hand-debug a second rotation formula — the same class of mistake twice — kerbs are now drawn directly from `boundary_segments`, the same boundary geometry the collision tests already validate, so the visible kerb is guaranteed to match what actually blocks the car and there is no rotation table left to get wrong. Separately, tiles still didn't connect seamlessly even after that: the vendored straight tile's composite is a non-square 512×688 canvas, and forcing it square before rotating a `STRAIGHT_NS` tile 90° left it occupying a swapped, misaligned on-screen footprint. Net fix: **replaced per-`TileKind` bitmap tile art with one uniform, undirected asphalt fill** (`Road_01_Tile_05`, a plain edge-to-edge 512×512 crack texture with no kerb baked in, placed identically under every cell) **plus the procedurally-drawn kerbs above** — this supersedes this doc's "Tile art" requirement text (composite-or-layered per-`TileKind` art), replaced above with the uniform-fill-plus-procedural-kerb description. The vendored `road_01/straight/` and `road_01/curve/` art (composites and layers alike) is no longer used and was removed from the repo. Lesson: for this project, a headless screenshot check is not a substitute for actually driving the thing — every one of these bugs was caught within seconds of interactive play, not before.

- 2026-09-12 — Second feel-tuning pass: hitting a wall killed almost all speed (the collision resolver removed the *entire* into-wall velocity component, per `collision.py`'s original design), which felt like getting stuck rather than a graze. Added a `wall_friction` constant (default `0.15`) so only that fraction of the into-wall component is removed — the boundary is still a hard collider (position is still clamped so the car can't cross it) either way, only the speed lost on contact changed. A low `wall_friction` is purely a Phase 1 human-play comfort choice, not a training-signal concern: once Phase 3 wires up off-track detection, a genome hitting a wall is expected to lose its episode via `terminated` regardless of how much speed this resolver happens to leave it, so making the wall less punishing here doesn't make training more forgiving.
