# Phase 7 — Dashboard: Control Panel

Status: **FINALIZED** — the requirements below are settled as of 2026-09-16; changing them needs a deliberate revision (see `../WORKFLOW.md`). Next is the Implementation plan section, then code.

## Goal
The first dashboard slice: run control and live scalar metrics, working while the sim runs headless.

## Requirements
Carried over from the 2026-09-09 decisions pass, plus decisions from the 2026-09-14 exploration pass (interrupted mid-session, recovered on 2026-09-15 from the local session transcript rather than lost — see Revision history), plus the 2026-09-16 pass that resolved the metric push cadence/schema below. The former dependency blocker — Phase 0's `Trainer.update_config`, and `NeatTrainer` actually implementing it — is now resolved: both are implemented (see [`../superpowers/plans/2026-09-15-neat-trainer-update-config.md`](../superpowers/plans/2026-09-15-neat-trainer-update-config.md)), though only for 3 of Phase 5's 7 live-changeable knobs (`max_generation_steps`/`max_generations`/`target_fitness`), so this phase can build the update mechanism now but the set of fields it can actually push live is still limited.

- **Stack:** FastAPI + WebSocket backend, React frontend. "No shared memory" describes the browser↔backend link only.
- **Process model:** the dashboard backend **embeds the trainer in-process** — the FastAPI process itself drives `NeatTrainer.run()` on a background thread/asyncio task and holds the live `Trainer` object in memory. A live config change is therefore a direct in-process call, not IPC. Trade-off accepted: one training run per backend process; multi-process support is not in scope for this phase. This also **resolves** the former "how does the dashboard discover/attach to a running trainer" open question — there is nothing external to discover, the trainer only exists inside a running backend process.
- **Live config updates go through the Phase 0 `Trainer` protocol, not backend-specific glue:** `Trainer` gains a `update_config(partial)` method — thread-safe, stages a pending change, applied atomically at the top of the next generation. Keeps Phase 7 backend-agnostic (NEAT now, Phase 10's RL backend later implements the same method) rather than poking `NeatTrainer` internals directly. Applied to Phase 0's own doc on 2026-09-15 (status → REVISED there, then → FINALIZED the same day once `NeatTrainer` implemented it) — the Protocol carries this method and `NeatTrainer` now implements it, for `max_generation_steps`/`max_generations`/`target_fitness` (3 of Phase 5's 7 live-changeable knobs). Phase 7 can build against the mechanism now; live-editing the rest of that knob list is still unwired.
- **Full resume flow from the dashboard**, not just fresh starts: starting a run offers "new model" or "resume existing model" (from Phase 6's model list). Resuming pre-fills the form with the model's last-known settings (Phase 6's "opens with most recent settings" rule) and surfaces current generation vs. `max_generations`/`target_fitness` so they can be raised before starting — avoids the "trains one more generation and silently stops" trap Phase 6 flagged for this phase to fix.
- **Live scalar metrics — revised for Phase 4's 2026-09-15 concurrent-batch evaluation model** (a generation's whole population batch starts and ends together; see `phase-4-learning-backend-neat.md`'s Revision history). There is no meaningful "genome N of population_size" sequential counter any more. While a generation is in progress: **active genomes remaining this round** (population_size minus genomes that have already crashed/finished out on their own — reaches 0, or ends the instant one genome succeeds), **elapsed steps vs. the per-generation step ceiling**, and **best fitness-so-far among genomes that have already finished or crashed out**. Once a generation completes: the full `TrainingUpdate` (Phase 0) — generation #, best/mean/worst fitness, population size, champion metrics, sim/wall time — not just the subset a first UI pass happens to render, so a later dashboard iteration (e.g. Phase 9) can surface more of it with no schema change. **"Alive count" is dropped** (leftover language from the pre-2026-09-10 shared-space design; meaningless under isolated-batch evaluation). **"Current sim speed" is dropped from this push schema too** — it names `RunConfig.sim_speed` (Phase 5), a config value the dashboard backend already holds and can serve via a plain config read, not a trainer-produced metric; mixing a config echo into the metrics-push channel isn't worth it.
  - **Progress mechanism:** `NeatTrainer` exposes a thread-safe, read-only progress snapshot; the dashboard backend's own timer polls it and pushes over WebSocket. **WS push cadence is decoupled from simulation ticks** — driven entirely by the dashboard backend's own timer, not by anything inside the evaluation loop — so a fast/slow run pushes at the same rate; this is the property "poll-driven" is actually about. Making that snapshot data available at all still needs one small, additive, backward-compatible parameter on `evaluate_batch` (Phase 4) that it writes into at each round boundary — a correction to this doc's earlier claim of "no change to Phase 4's evaluation code path," caught while writing the Implementation plan; see Revision history.
  - **Push cadence:** a fixed wall-clock interval, always pushed (not only on change) so a silent connection is distinguishable from a stalled backend. **The interval is itself a dashboard control-panel knob** — adjustable at any time with immediate effect (a plain timer restart, no generation-boundary rule needed, since it affects nothing but push rate) — defaulting to **200ms**. Dashboard-only runtime state: not a `RunConfig` field, not written to Phase 6's settings-history (it has no bearing on training reproducibility, only on how often the backend talks to the browser), and global per backend process (matching the existing one-run-per-process model).
  - **WebSocket message schema:** one JSON envelope shape, `{"type": ..., "schema_version": 1, "data": {...}}`, `type` one of:
    - `"progress"` — pushed on the cadence above while a generation is running. `data`: `generation`, `population_size`, `active_genomes_remaining`, `elapsed_steps`, `step_ceiling`, `best_fitness_so_far` (`null` until any genome has finished/crashed).
    - `"generation"` — pushed once when a generation completes. `data`: the full `TrainingUpdate` (its own `schema_version` field rides along inside `data`, independent of the envelope's).
    - `"status"` — pushed once on each run lifecycle transition, reusing Phase 6's exact `runs.status` enum (`persistence/runs_repo.py`) rather than inventing a parallel one, so the dashboard's live status and the persisted run status always read the same way. `data`: `state` (`"running"` / `"completed"` / `"crashed"` / `"stopped"`), `detail` (string or `null`).
  - Also flagged, out of scope for this phase: watching the whole batch step visually in real time belongs to Phase 8, not Phase 7 (this phase has no in-browser rendering at all — see below).
  - Live edit of the rest of the live-changeable config subset (defined in Phase 5) beyond the update-mechanism question above.
  - Basic run list + history view (data from Phase 6).
- **No in-browser rendering in this phase** — a run is watched locally via the `arcade` renderer. The in-browser live view is Phase 8.
- **Local-first:** binds to localhost, single user, no auth. The architecture must not preclude adding auth + remote deployment later ("local-first, remote-capable by construction").

## Revision history
- 2026-09-16 — Cross-phase gap found while writing the Implementation plan (not during the brainstorming pass below): the "no change to Phase 4's already-FINALIZED evaluation code path" claim in the Progress mechanism decision was wrong. `evaluate_batch` runs a whole generation's round-robin loop internally and returns only once the batch finishes — `NeatTrainer` never sees mid-batch state at all, so a poller has nothing to read unless `evaluate_batch` itself writes progress somewhere as it goes. Corrected in place above: `evaluate_batch` gains one small, additive, backward-compatible parameter (default `None`, zero behavior change for existing callers/tests) that it updates at each round boundary. The actual decision — WS push cadence is driven by the dashboard backend's own timer, not by anything inside the evaluation loop — is unaffected; only the implementation-detail prediction about evaluation.py was wrong, not the architecture.
- 2026-09-16 — Resolved the last open question (metric push cadence/WebSocket schema) via a brainstorming pass, closing this doc: DRAFT → FINALIZED.
  - **Progress mechanism:** decided against threading a callback through Phase 4's `evaluate_batch` hot loop (would touch already-FINALIZED code); `NeatTrainer` instead exposes a read-only progress snapshot the dashboard backend polls on its own timer. Poll-driven also decouples push rate from simulation speed.
  - **Cadence:** fixed-interval, always-push (not only-on-change) so a silent WS connection reads as "nothing changed" rather than "backend died." Made the interval itself a dashboard control-panel knob (user's explicit request, this session) rather than a hardcoded constant — default 200ms, dashboard-only runtime state (not `RunConfig`, not settings-history — it doesn't affect training reproducibility), global per backend process, adjustable with immediate effect.
  - **Schema:** one WS envelope (`{"type", "schema_version", "data"}`) over three message types — `progress` (in-progress batch state, matching this doc's existing live-metrics-content decision), `generation` (the full `TrainingUpdate` passthrough, not a hand-picked subset, so later phases can surface more of it with no schema change), and a new `status` type for run lifecycle transitions (surfaced as a gap during this pass: nothing previously told a WS client when a run ended, or why). `status` reuses Phase 6's exact `runs.status` enum (`running`/`completed`/`crashed`/`stopped`) rather than inventing a parallel one — that table's docstring already reserved `"stopped"` for exactly this dashboard control surface.
  - **Dropped "current sim speed"** from the completed-generation content this doc had listed since 2026-09-15: it turned out to name `RunConfig.sim_speed`, a config value with no producer inside `NeatTrainer`/`TrainingUpdate` at all (Phase 5's own knob classification already flagged it as unwired, having no consumer anywhere in the codebase yet) — a config echo, not a trainer metric, so it doesn't belong on this push channel. The dashboard backend already holds it in-process and can serve it via a plain config read instead.
