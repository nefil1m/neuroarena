# Phase 4 — Learning Backend: NEAT

Status: **FINALIZED** — requirements settled as of 2026-09-13, revised 2026-09-15 (concurrent batch evaluation + collective finish-early trigger), implementation caught up the same day. Changing them needs a deliberate revision (see `../WORKFLOW.md`).

## Goal
NEAT neuroevolution end-to-end on the car game, running both headless and rendered.

## Requirements
Settled through the 2026-09-13 Phase 4 exploration pass (carried over 2026-09-09 platform requirements, plus resolution of all prior open questions and the cross-phase gaps a validation pass against Phase 3/Phase 5 found).

- **NEAT is one of several peer learning backends** behind the Phase 0 Model/Trainer interface. It consumes the same Environment and config as any other backend. Deep RL is Phase 10; more backends may follow.
- **Genome → network** maps the 10-float observation to the 2-float continuous action via **`tanh` on both output neurons**, giving `[−1, 1]` directly with no separate clipping step. Chosen over a raw linear output hard-clipped to range: `tanh` stays smooth and gives mutation a gradient everywhere, where clipping produces flat, information-discarding saturated regions.
- **Runs headless** (fast, no rendering) and with the `arcade` renderer attached. Rendering is never required.
- **Each genome is evaluated in isolation** on its own copy of the track — no other cars, no car-to-car interaction, no shared physics. Isolation is about *state*, not *execution order*: genomes in a generation's batch are stepped **concurrently**, not one full episode at a time — see "Generations always terminate" below for the two conditions that end a batch, and Revision history for the concurrency mechanism this pass decided. This still keeps per-genome fitness clean (no genome's outcome depends on any other's actions) while producing a tick-by-tick view of the whole batch advancing together, which the collective stop condition below relies on and Phase 8's later live view can reuse. The generational loop is **batch**: evaluate the whole population's batch, then select and breed the next generation.
- **Fitness comes from the `Objective`** (Phase 0 interface; concrete objectives in Phase 5), read via `Objective.fitness()`. Never baked into the backend.
- **A force-truncated individual is scored on partial progress**, exactly like a normally-ended episode: the trainer calls the same `Objective.fitness()` on whatever state the individual reached before it was cut off, with no separate penalty term. Keeps fitness continuous across truncated and non-truncated individuals and avoids a fitness cliff that could distort speciation.
- **Per-generation records.** The trainer emits a `TrainingUpdate` per generation (fitness distribution, champion metrics, species count). **Every generation's champion genome is saved** (config-gated, per Phase 6 storage/retention), so any generation can be re-simulated later — the sim is deterministic given `(seed, genome)`, so the genome plus seed is enough, no stored trajectory.
- **Generations always terminate**, on whichever of two triggers fires first:
  1. **The per-generation step ceiling** (from config) is exhausted — every genome still running is force-truncated (scored per the rule above).
  2. **A genome finishes** — the instant any genome's episode ends via `Objective.should_stop()` (task success; not a crash/`terminated`, and not trigger 1), every *other* genome still actively running in the same batch is force-truncated too (scored per the rule above) and the generation advances immediately. Rationale: once one genome has succeeded, no genome still mid-episode can out-score it for breeding purposes, so letting the rest keep running only spends wall-clock time for no benefit.

  Together with the per-episode `truncated` limit, a generation cannot hang on an individual that neither crashes nor finishes. **`RunConfig` does not yet carry the step-ceiling field** (Phase 5 owns the full config-knob classification pass) — Phase 4 adds the minimal field itself (e.g. a generation step/time ceiling) as a stub ahead of that pass, per `../WORKFLOW.md`'s "a stub or reserved field is the right depth" rule, so Phase 4 isn't blocked on Phase 5 reaching FINALIZED first.
- **Mid-run track switches (Phase 5, live-changeable) take effect at the next generation boundary.** A switch is recorded immediately in the settings history like any other live config change, but the population's `make_env` closures aren't rebuilt onto the new track until the current generation's batch finishes — every individual within one generation is compared on the same track, preserving the "clean per-genome fitness" rationale isolation exists for in the first place.
- **The per-ray boundary-distance check's `O(segments)` cost (flagged by Phase 3 as a `TODO(phase-4)`) is explicitly deferred, not addressed now.** Build the straightforward version, measure actual per-generation wall-time at a realistic population size once there's a real training loop to profile, and only add a broad-phase spatial lookup if profiling shows it's the bottleneck — track sizes so far (Phase 2) are small polygons (tens of segments), not thousands.
- **Speciation and hyperparameter defaults use `neat-python`'s own stock example config as-is** — a documented starting point, not hand-derived for this task, in the same spirit as Phase 3's ray-range constants ("tunable... once actually driven"). Real tuning happens once there's an actual training loop to observe and iterate against.
- Checkpoint / resume and the settings-history requirement (Phase 6) apply, with NEAT-specific state (population, genomes, innovation history).
- **NEAT implementation: `neat-python`.** Mature, widely-used, handles genome mutation/crossover/speciation and config-file hyperparameters. Traded off against a custom implementation (full control over genome representation and this project's own config/serialization conventions, at the cost of reimplementing crossover/speciation correctly from scratch for a well-solved problem) — the user chose the existing library.

- 2026-09-15 — **Deliberate revision** (per `../WORKFLOW.md`): genomes within a generation's batch now execute **concurrently** instead of the sequential `for genome in genomes: evaluate_genome(...)` loop actually built, and a **second generation-termination trigger** is added — a genome finishing (`Objective.should_stop()`) force-truncates every other still-running genome in the batch immediately, rather than each genome only ever stopping on its own crash/finish/the shared step ceiling. Surfaced from a brainstorming session on 2026-09-14 that was interrupted (computer shutdown) before being written back — recovered from the local session transcript rather than lost. Root cause: the 2026-09-10 scope cut (see below, same date) collapsed "batch vs sequential" into "batch only" at the *generation* level (whole population evaluated before breeding, replacing the rejected "kill one genome → immediately spawn the next generation" idea) but left genome-level *execution order within* a batch unspecified; the implementation filled that gap with the simplest option (sequential), which technically satisfied this doc's text but not the original intent — a full generation should run and be watchable as one batch, and a batch shouldn't keep running genomes that can't possibly beat a genome that already finished. **Concurrency mechanism:** round-robin lockstep — one `env.step()` per still-active genome per round, cycling through the batch — chosen over real OS-level parallelism (multiprocessing) after measuring the actual per-tick cost on this repo's `CarEnvironment` (`env.step()` ~210µs, genome forward pass ~3µs, ~4,500 combined genome-ticks/sec single-threaded): round-robin needs no IPC/picklability handling and keeps `StepBudget` a single shared counter, at the cost of no multi-core throughput gain (out of scope for now; a later perf pass if profiling ever shows it's needed). This also **resolves for free** the fairness trade-off the 2026-09-13 entry below accepted (a genome evaluated later could be force-truncated by budget exhaustion purely due to evaluation order) — round-robin consumes the shared step budget evenly across every active genome each round, so there is no more "evaluation order" to be biased by. Ripple check: `generation_stats` (Phase 6) and `ProgressObjective`/fitness (Phase 5/6) need no changes — the former already records one aggregate row per generation regardless of internal evaluation order, the latter's `should_stop()` was already exactly the right "finished" signal, it just didn't previously propagate beyond its own genome. Phase 7's stalled "what do live metrics show mid-generation" question is answered by this: there is no per-genome progress counter to show (the whole batch starts and ends together), see Phase 7's doc.

- 2026-09-13 — Confirmed as a deliberate design choice, not a bug: the per-generation step budget is one shared counter consumed sequentially across the population, so a genome evaluated later can end up force-truncated (fitness reflecting fewer or zero steps) purely because earlier genomes in evaluation order consumed more of the budget, not because of its own merit. Raised during the final whole-branch review as a fairness question (an alternative would split the budget evenly per genome, e.g. `max_generation_steps // population_size`). Kept as-is: only matters when `max_generation_steps` is set well below `population_size × typical episode length`, which the platform default (300k steps / 150 population) never triggers.
- 2026-09-13 — Final whole-branch review fix wave (implementation-level only; no requirement reopened). Five findings fixed, all reproduced empirically first:
  - **Checkpoint resume lost NEAT's id allocators.** `neat.Population.__init__` always builds a *fresh* `DefaultReproduction`/`DefaultSpeciesSet` even when handed an `initial_state`, resetting `genome_indexer`, `ancestors` and the species `indexer`. A resumed run therefore minted offspring ids starting from 1 again; since `DefaultReproduction.reproduce` writes elites and offspring into the same dict, elites were silently overwritten and the population shrank (reproduced: `pop_size=20` → 18 one generation after a round trip). Fixed by re-deriving all three counters — including `DefaultGenomeConfig.node_indexer`, found during the fix — from the restored keys at load time (monotone by construction, so no counter is stored), and persisting `reproduction.ancestors`, which is real lineage data rather than a counter. This also closes the parked `itertools` `DeprecationWarning` below at its root instead of suppressing it: no `itertools.count` is pickled any more, so the checkpoint stays loadable on Python 3.14, where that pickling becomes a `TypeError`.
  - **`champion_dir` and cumulative `sim_time` were dropped on resume** — champion capture silently turned off and `TrainingUpdate.sim_time` restarted from zero. Both now ride in the payload and are restored. `wall_time` stays deliberately per-process and unpersisted.
  - **`load_checkpoint` performed no descriptor compatibility check.** Per Phase 0 the checkpoint now records its observation/action descriptors and a resume into a shape-mismatched environment is refused with `IncompatibleDescriptorsError` instead of failing deep inside network evaluation.
  - **Champion metrics were hard-coded to car-specific `info` keys**, violating the "must not assume car-ness" goal (and returning all-zeros for any other environment). They are now derived from whatever numeric values the champion's own evaluation `info` carried — unchanged for the car (`crashed`/`progress`/`lap_progress`, with the `str` `track_id` excluded).
  - Checkpoint `schema_version` bumped to **2**: the payload shape changed, so a v1 file is now rejected with the existing clear error rather than failing on a missing key.
