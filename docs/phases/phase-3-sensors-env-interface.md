# Phase 3 — Sensors & Environment Interface

Status: **FINALIZED** — the requirements below are settled as of 2026-09-12; changing them needs a deliberate revision (see `../WORKFLOW.md`). Next is the Implementation plan section, then code.

## Goal
Implement the car game's observation and action spaces and wire the game to the Phase 0 Environment interface.

## Requirements
Settled through the 2026-09-12 Phase 3 exploration pass (carried over 2026-09-09 platform requirements, plus resolution of all prior open questions and new `terminated`/`info` scope).

- **Observation vector (v1): 10 floats, normalised** — 7 raycasts + normalised speed + last action (previous steering, previous throttle).
- **Raycasts:** 7 rays in a forward-dense fan `[−75, −45, −20, 0, 20, 45, 75]°` relative to car heading. Value is **proximity** `1 − d/range`, clamped to `0` when nothing is within range (a miss reads identically to a hit exactly at the range boundary — both are "clear"). Rays detect the **track boundary only** — there are no other cars in the simulation, since each genome is evaluated in isolation (Phase 4).
- **Ray range is speed-scaled:** `range = 300 + 200 · speed_norm` (world units), capped at `max_range = 600`. Anchored to Phase 1's car length (`100` units) and the "few car-lengths" relationship Phase 2 assumed when it deferred these numbers here: `3` car-lengths at rest, growing to `~5` at full forward speed, giving enough forward lookahead to anticipate a turn without every ray saturating at `0` on a wide-open straight. Starting values, tunable like Phase 1's physics constants once actually driven.
- **Sensor layout is configurable at run creation** (ray count, angles, range params); the values above are the platform-standard default. A non-default sensor config changes the observation shape, so it starts a fresh model rather than resuming an existing one (per the Phase 0 model/config compatibility check).
- **Speed normalisation is signed, on a single scale:** `speed_norm = speed / max_speed` (Phase 1's `750 units/s`), so forward motion ranges `[0, 1]` and reverse ranges down to about `-0.4` (Phase 1's `max_reverse_speed = 300`). A single shared scale — rather than each direction separately normalised to `±1` — preserves the true relative magnitude between forward and reverse speed.
- **"Last action" is the raw commanded action** — the env echoes back the `(steering, throttle)` it was given in the previous `step()` call, not a value reconstructed from physics. It defaults to `(0, 0)` in the observation `reset()` returns, before any action has been commanded.
- **Action space:** continuous `Box`, 2 dimensions, each `[−1, 1]` — steering, throttle. Exposed as a typed descriptor per the Phase 0 contract.
- The car game implements the Phase 0 Environment interface. Its observation and action descriptors are what the Phase 0 model/config compatibility check compares.
- **`terminated` fires on any contact with the track boundary.** The hard physical collider Phase 1 built stays exactly as it is — the car still cannot cross the boundary — and a genome touching the wall loses its episode via `terminated` on that same tick, regardless of the residual speed Phase 1's `wall_friction` resolver leaves it. There is no separate "off-track" state and no soft deviation buffer. This is the car env's only in-world end: there is no in-world "finish", since the track is a closed loop with no finish line of its own — lap/checkpoint-based stopping is an `Objective.should_stop()` concern (Phase 5), not a `terminated` case.
- **The car Environment enforces a configurable maximum episode length** (step count and/or sim-time) and sets `truncated` when it is hit, per the Phase 0 flag contract. The limit is a config parameter (Phase 5), never hard-coded. This is the single-agent "stuck forever" guard; the population-level per-generation ceiling is Phase 4.
- **`info` carries:** `crashed` (bool, mirrors `terminated`); `track_id` (which stored map, Phase 2, this episode runs on); `progress` (the car's current position along the track's centerline, measured as signed distance from the spawn point — continuous and unwrapped, so it keeps increasing lap after lap when driving the intended direction and can go negative if the car reverses past the start, never resetting or jumping at the lap boundary); and `lap_progress` (the same measurement as a fraction of one full loop, so `1.0` = one lap, `2.3` = partway through the third — self-normalising across differently-sized tracks). These are the raw, game-specific facts a Phase 5 `Objective` needs (e.g. to detect a completed lap, or shape reward on progress) without requiring access to the `Track` object it is never given.

None remaining at the requirements level — see Revision history for how each item was resolved. Implementation-level details (the raycast origin point on the car body, exact `SensorConfig` field names, defensive action clipping, how `progress` is computed from the cell-sequence path) are left to the Implementation plan.

## Implementation plan
Detailed, step-by-step plan: [`../superpowers/plans/2026-09-12-phase-3-sensors-env-interface.md`](../superpowers/plans/2026-09-12-phase-3-sensors-env-interface.md).

Four tasks, each ending in an independently testable, committed deliverable:
1. **Boundary raycasting geometry** (`sim/raycast.py`) — pure ray/segment intersection, independent of `Track`/`TileKind`.
2. **Track loop length and boundary-contact detection** — a `track_loop_length` helper added to Phase 1's `track.py`, and a `distance_to_boundary` helper added to Phase 1's `collision.py`.
3. **Observation vector assembly** (`sim/observation.py`) — `SensorConfig`, speed normalisation, and `build_observation` combining raycasts + speed + last action into the 10-float vector.
4. **`CarEnvironment`** (`sim/car_env.py`) — the `Environment` Protocol implementation: wraps Phase 1's `Game` unmodified, adding `reset`/`terminated`/`truncated`/`info`.

Nothing in `sim/game.py` or `sim/physics.py` changes — `CarEnvironment` composes `Game` exactly as Phase 1's own docstring anticipated ("that's Phase 3's `Environment` concern").

- 2026-09-13 — Implemented all four Implementation-plan tasks (`neuroarena.sim.{raycast,observation,car_env}`, plus the `track_loop_length`/`distance_to_boundary` additions to `track.py`/`collision.py`), 112 tests passing, clean `ruff`/`mypy --strict`. One implementation-level finding changed how a requirement is met (not what it requires): **the plan's first pass at `progress` computed it as an odometer** (the car's own signed speed integrated over time) **instead of the centerline projection this doc's `info` requirement actually specifies**, discovered by a whole-branch review before merge. The odometer was not just non-compliant wording — it was exploitable: a genome driving in a tight circle (radius ~257, which fits inside a curve tile's drivable annulus at this project's physics constants) could accumulate unbounded `progress` without ever advancing around the track, since the odometer measures raw motion, not net position. Escalated to the user rather than fixed unilaterally, per this project's standing rule that the user decides feature behavior (the same rule Phase 2's history invoked for its own size-distribution finding). **Decided: implement true centerline projection** — a discretized polyline down the middle of the track (`track.centerline_path`, radius `cell_size/2`, matching `track_loop_length`'s analytic centerline) plus nearest-point-on-polyline projection (`track.project_onto_centerline`), with `CarEnvironment` tracking the car's projected position as a continuous, unwrapped arc-length delta each tick (the same continuity/sign properties this doc already specified, now actually measuring the right thing). This closes the exploit: circling in place projects to a locally-stable nearby point, so per-tick deltas stay small instead of accumulating. Also fixed in the same pass, from the same review: the observation could exceed its own declared `Box(-1,1)` bounds because the last commanded action was stored unclipped (now clipped to `[-1,1]`, still "the raw commanded action" for any legal input); `CarEnvironment.step()` and `build_observation()` had no docstring naming the `info` keys / observation slot layout (added); `raycast.cast_rays()` divided by zero when `SensorConfig`'s range-clamp formula legitimately produces `max_dist = 0.0` at extreme reverse speed (now guarded). One negligible, parked finding: `project_onto_centerline`'s discretized-polyline length differs from `track_loop_length`'s analytic value by roughly `0.05%` per lap (curve-arc discretization) — self-documented in code, orders of magnitude smaller than anything that affects the wrap-around logic that depends on it, not worth fixing.
