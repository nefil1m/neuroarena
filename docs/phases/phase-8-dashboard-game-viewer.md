# Phase 8 — Dashboard: Game Viewer

Status: **FINALIZED** — requirements and design settled 2026-09-18; changing them needs a deliberate revision (see `../WORKFLOW.md`). Next is the Implementation plan section, then code.

## Goal
Watch a training run on the real game: the existing `arcade` renderer, extended to show a whole generation's batch at once, opened and controlled from the dashboard's control panel.

## Requirements
Settled in the 2026-09-18 exploration pass.

- **The viewer is a native `arcade` window, not a browser view.** The dashboard stays a settings-and-metrics control panel; the browser does not draw the game. The panel gets an "open game window" / "close" control that spawns the viewer, plus the view settings below. (This revises the earlier framing of this phase as an in-browser live canvas — see Revision history and the rejected alternatives below.)
- **What the viewer shows: the whole batch, live.** Because Phase 4's concurrent-batch evaluation steps every genome of a generation in lockstep (each on its own isolated copy of the track, no interaction), all of them are running at the same instant. The viewer draws every still-active car on the track at once as non-interacting "ghosts"; a car that crashes or finishes drops out, so the field thins over the generation; the current best car is highlighted. No single-genome mode, no overlaid-trajectory mode, no montage.
- **The `arcade` renderer is extended, not duplicated.** Multi-car drawing and a camera with zoom and three selectable camera modes — **fit the whole track**, **follow the best car**, and **follow a chosen car** (all three decided 2026-09-18) — are added to the existing render layer. The same view is available to any other consumer of that layer.
- **The viewer is a separate process and a client of the dashboard API.** The trainer, dashboard backend and viewer talk only over that API (the platform rule in `../OVERVIEW.md`); the viewer reads car positions from the backend over its WebSocket and never touches the trainer directly. Positions are obtained the way Phase 7 obtains its progress snapshot: the backend samples the trainer's state on its own timer, decoupled from simulation ticks, with no hook inside the evaluation loop. **The backend samples and pushes car poses to the viewer at a fixed 60 Hz** (decided 2026-09-18) — matching the game window's refresh rate so motion is smooth at real-time speed; no adjustable rate, no client-side interpolation.
- **View settings are controlled from the panel:** zoom, camera mode, which car to follow. **A car to follow is chosen from the panel by rank** ("follow #1 … #N", ranked live); the choice is held until that car drops out, then the camera falls back to the best remaining car so it never sits on an empty spot (decided 2026-09-18). No click-to-select in the viewer window. The panel sets them through the backend, which forwards them to the running viewer.
- **The viewer loads the track and sprite assets itself.** The backend tells it the `track_id`; the viewer loads the track from the shared data directory and reads the asset manifest with the loaders the game window already uses. No track or asset endpoints on the API (decided 2026-09-18; possible because viewer and backend share a machine).
- **A speed control paces the trainer so a run is watchable (decided 2026-09-18).** Today the trainer is unpaced — training runs as fast as the CPU allows and `RunConfig.sim_speed` has no consumer anywhere in the codebase — so a viewer on an unpaced run would show a fast-forward blur. This phase wires up speed pacing: from real time and slower/faster steps up to "max" (unpaced), changed live from the panel with immediate effect. The panel offers a fixed set of presets, not a free value: 0.25×, 0.5×, 1× (real time = each step takes the game's fixed 1/60 s timestep), 2×, 4×, 8× and Max. The default stays "max", so training is as fast as possible when nobody is watching; choosing a slower speed while watching deliberately slows training. This adds a small, additive pacing hook to Phase 4's evaluation loop (and gives Phase 5's stub `sim_speed` field its first consumer).
- **The speed setting is dashboard-only runtime state, not a `RunConfig` field (decided 2026-09-18).** Same treatment as Phase 7's poll interval: not in `RunConfig`, not written to the settings history, global per backend process, defaults to Max every time the backend starts. Speed never affects results (the fixed timestep keeps runs deterministic), so nothing is lost by not persisting it, and it avoids the trap of a later `neuroarena-train --resume` silently inheriting a real-time speed with no viewer. This revises Phase 5's classification of `sim_speed` as a plain live-changeable `RunConfig` knob (see that doc's Revision history). The now-unused `RunConfig.sim_speed` stub field is **left in place and documented as unused** (decided 2026-09-18) — removing a field from a versioned config would need a schema-version decision for no gain here; if ever wanted, a later schema-versioned cleanup can remove it along with the other consumer-less stubs (`track_id`, `headless`).
- **The viewer is never blank and never pauses (decided 2026-09-18).** At a generation boundary the view cuts straight to the new batch (every car back at the start). With no run active, the window stays open showing the last run's track with a "waiting for a run" label and starts drawing the moment a run starts, so it can be opened before a run. When a run ends it keeps the last frame with the final status (e.g. "stopped"). It does not close itself when a run ends.
- **The backend owns exactly one viewer (decided 2026-09-18).** "Open game window" asks the backend to spawn the viewer as a child process; a second Open while one is running does nothing. Closing the window by hand is fine and the panel shows it as closed; a viewer that crashes is likewise shown as closed. When the backend shuts down it terminates the viewer, through the same lifespan shutdown hook that finalizes run rows. No multiple viewers, and no standalone launch command.
- **A small text overlay, panel-only control (decided 2026-09-18).** The viewer window shows the generation number, cars alive out of total, the current speed, and the camera mode with the followed rank. All control stays in the web panel — no keyboard shortcuts in the window, so there is one place that owns the view settings.
- **Rank is `Objective.fitness()`, read live per car (decided 2026-09-18)** — the same number NEAT scores on. For the current driving objective that is cumulative progress along the track, so rank order is "furthest around the track first". The objective is already stateful per genome and updated every step, so the viewer's snapshot reads it with no new bookkeeping, and the ranking follows automatically if the objective changes. Not defined directly as raw track progress.
- **Same-machine only, by nature.** A native window can only show on the machine running the trainer; the control panel itself remains usable remotely. Accepted.
- **Verified precondition:** the `arcade` game window opens and is playable on the project's WSL2 setup (confirmed 2026-09-18), so a window-based viewer is viable.
- **Independent phase** — reorderable relative to Phases 9 and 10, and other work may be inserted before it.

### Alternatives considered and rejected (2026-09-18)
- **Second renderer in the browser** (canvas/WebGL drawing the same tiles, kerbs, decor and car sprite from the same PNG assets): duplicates the game's drawing rules in TypeScript, with drift risk whenever the art rules change.
- **Stream the real game to the browser** (offscreen `arcade` render, JPEG/MJPEG frames): one renderer, but it depends on offscreen OpenGL working under WSL2 (a documented risk for this project), costs server CPU for rendering and encoding, and offers no zoom or follow control without more work. Not ruled out forever: the multi-car camera work built here is exactly what a later stream would render, so it can be added on top without redoing this phase.
- **Earlier same-day decisions, superseded:** a separate ~30 fps position stream to a browser canvas (moot without browser rendering); "what else goes on the canvas" (moot — the viewer draws what the game draws).

### Design
How the pieces fit (settled 2026-09-18):
- **Trainer side — two small additive changes to the NEAT backend.** (1) A thread-safe, read-only car snapshot on `NeatTrainer`: for each car, position, heading, live `Objective.fitness()` and whether it is still alive — same read-only shape as Phase 7's progress snapshot, with no hook inside the simulation loop. (2) A pacing hook: `evaluate_batch` takes an optional speed provider and sleeps once per round so a round takes `1/60 s ÷ speed`; "Max" means no sleep (today's behavior).
- **Backend.** `RunManager` holds the speed preset as runtime state (`GET`/`PATCH /api/speed`). A `ViewerManager` owns the one viewer child process (spawn, terminate, is-running), with `POST /api/viewer/open` and `/close`, `GET /api/viewer`, and `PATCH /api/viewer/settings` (zoom, camera mode, followed rank); shutdown terminates the viewer. **A new WebSocket endpoint `/ws/viewer`** carries the 60 Hz car frames and view-setting changes to the viewer, in the same envelope shape (`{"type": ..., "schema_version": 1, "data": ...}`). The panel's existing `/ws` is unchanged — it keeps exactly its three message types and never sees 60 Hz traffic.
- **Viewer window (render layer).** The `arcade` window reuses the game's track, tile and kerb drawing and draws N car sprites, with the three camera modes, zoom and the text overlay. The camera math and follow logic (fit / follow best / follow #N with fall-back to the best remaining car) live in a plain module with no OpenGL, so they are unit-testable; the window only draws. A background thread reads `/ws/viewer` into a "latest frame" slot the draw loop reads. The window loads the track and manifest itself by `track_id` and shows "waiting for a run" when idle.
- **Panel (React).** A speed preset selector, and a "Game window" box: Open/Close, camera-mode selector, zoom, follow-rank control.
- **Errors.** If the viewer cannot reach the backend it shows "disconnected", retries, and exits if the backend stays gone; a track that fails to load shows an overlay message; a viewer that dies shows as closed in the panel.
- **Testing.** Unit tests for the snapshot, the pacing (with a fake clock), the view model, the viewer manager (with a fake subprocess) and the new REST and WebSocket routes. The actual `arcade` drawing gets a manual check, since it needs a real window.

## Open questions
None remaining at the requirements level. Implementation-level details left to the Implementation plan: the exact fields and thread-safety shape of the trainer's additive car-pose snapshot (position, heading, live `Objective.fitness()`, alive flag — same read-only shape as Phase 7's progress snapshot), the pacing hook's exact signature in `evaluate_batch`, and how `arcade`'s main-thread event loop, the viewer's connection thread and the spawn/terminate channel fit together (the reason the viewer is its own process).

## Implementation plan
Detailed, step-by-step plan: [`../superpowers/plans/2026-09-18-phase-8-game-viewer.md`](../superpowers/plans/2026-09-18-phase-8-game-viewer.md).

Thirteen tasks, each ending in an independently testable, committed deliverable:

1. `Visualizable` protocol + `CarEnvironment.visual_state()`.
2. `evaluate_batch`: live-genome publication and the per-round `pace` hook.
3. `NeatTrainer.visual_snapshot()` and `set_pace()`.
4. `dashboard/pacing.py`: speed presets and `Pacer`.
5. `RunManager` speed state, pacer wiring, visual snapshot; `/api/speed`.
6. `render/view_settings.py` (pure `ViewSettings`).
7. `render/view_model.py` (ranking, follow logic, camera, overlay — pure).
8. Viewer protocol messages and `ViewerManager`.
9. Viewer REST routes, `/ws/viewer`, shutdown and CLI wiring.
10. `render/viewer_client.py` (the viewer's backend connection).
11. `TrackScene` extraction and the viewer window.
12. Frontend: speed selector and game-window panel.
13. Docs, `sim_speed` note and end-to-end verification.
