# Phase 2 — Track Generation

Status: **FINALIZED** — the requirements below are settled as of 2026-09-12; changing them needs a deliberate revision (see `../WORKFLOW.md`). Next is the Implementation plan section, then code.

## Goal
Procedural tracks parameterised by size, complexity, and seed, renderable as a real track.

## Requirements
Settled through the 2026-09-12 Phase 2 exploration pass (carried over 2026-09-09 platform requirements, plus resolution of all prior open questions and new map-management scope).

- **Parameters: size, complexity, seed.** Generation is deterministic from the seed. `size` is the desired **tile count** of the closed loop — not an independent world-unit dimension; the world-unit footprint follows from `cell_size × tile count` per Phase 1's grid representation. `complexity` is the walk's **turn-frequency bias**: the probability of turning vs. continuing straight at each step (low = long straights, sparse turns; high = tight, turn-dense loops).
- **Output serves two consumers:** (a) collision geometry (drivable region + boundary) for the simulation, and (b) enough structure for the renderer to dress it as a real track — road surface, edge lines for kerbs, start/finish, spawn points, scenery hints.
- **Same track representation** as Phase 1's static-track path: a closed-loop sequence of grid cells, each a `TileKind` (straight or 90°-turn curve — see Phase 1), sharing the fixed `cell_size` world-unit constant. Generation means producing a valid closed loop of grid moves, not freeform geometry. Phase 2 becomes the source of tracks, superseding the hand-authored one.
- **Generation algorithm: self-avoiding random walk with retry-until-valid closure.** Walk the grid cell-by-cell, biased by `complexity`'s turn probability, backtracking whenever the walk traps itself; once within reach of the start cell, attempt loop closure back to it. A cell is never revisited mid-walk, so self-intersection is prevented **by construction**, not by a post-hoc check. If closure isn't reached within a step budget, the attempt is discarded and retried (same seed, next sub-attempt index) — generation must always eventually yield a valid closed, non-self-intersecting loop or a clear failure, never a partial or self-intersecting one. (Considered and rejected: template/piece-based assembly from pre-authored loop chunks — more authoring effort, less combinatorial variety, and reframes complexity as chunk-selection rather than path-shape.)
- **Requested size is a target, not a guarantee: ±15% drift is acceptable.** The retry-until-valid walk isn't guaranteed to close at exactly the requested tile count. Tightening the tolerance would mean more retries (slower generation) for sizes where an exact-length closed loop is hard to hit, especially small ones. A requested `size` below the minimum feasible closed loop (4 tiles — a 2×2 block of curves, the smallest loop expressible with 90°-only turns) is rejected.
- **Map identity and storage.** Each generated map gets a `track_id` and is written as its own JSON file — Phase 1's track format plus `track_id`, requested/actual size, complexity, seed, and `generated_at` — inside a `tracks/` directory, alongside a lightweight manifest (`track_id → {path, params}`) for enumeration without opening every file. Storage is **plain files, not SQLite**: Phase 6 (SQLite metadata) is implemented after Phase 2 in build order, so Phase 2 must be self-sufficient. Phase 6 later adds a `track_id` reference into its run/model metadata pointing at these same files — it indexes Phase 2's storage rather than Phase 2 reaching forward into unbuilt Phase 6 infrastructure, or a second, duplicate SQLite store appearing here.
- **Generation control surface (this phase): a CLI dev tool** (e.g. `uv run neuroarena-track-gen --size N --complexity C --seed S`) that generates, previews (reusing Phase 1's `arcade` renderer to draw the result), and saves a map via the storage above. Deliberately not a browser UI — Phase 7's dashboard backend doesn't exist yet in build order. Phase 9's already-reserved "track editor / regeneration UI" becomes a thin front end calling this same generation function later; no rework of this phase's core is needed when that happens.
- **Ray-range default is tied to a few car-lengths** (see Phase 3) so raycast sensors stay informative across generated track widths — a long fixed range saturates on narrow tracks and blinds the model.
- **Track lifecycle is user-driven** (per `../OVERVIEW.md`): training continues on a track until the user regenerates or switches. It is not a per-run success signal. See Phase 5 for how an in-progress run's active track is selected/switched, and Phase 6 for how a model's track history is recorded.

## Open questions
None remaining at the requirements level — see Revision history for how the generation algorithm, complexity mapping, self-intersection avoidance, size-drift tolerance, map storage, and the generation control surface were resolved. Implementation-level details (exact retry-attempt budget, manifest file layout, CLI flag names) are left to the Implementation plan.

## Implementation plan
Detailed, step-by-step plan: [`../superpowers/plans/2026-09-12-phase-2-track-generation.md`](../superpowers/plans/2026-09-12-phase-2-track-generation.md).

Four tasks, each ending in an independently testable, committed deliverable:
1. **`tile_kind_for_open_edges`** — the inverse lookup (open-edge pair → `TileKind`) the generator needs, added to Phase 1's `track.py`.
2. **`generate_track`** — self-avoiding random walk with `complexity`-biased turns, backtracking, and retry-until-valid loop closure within the ±15% size-drift tolerance.
3. **Map storage** — `TrackRecord`, `track_id`, a JSON file per map under `tracks_dir`, and a manifest for enumeration — plain files, not SQLite.
4. **CLI** (`neuroarena-track-gen`) — generate, save, and optionally preview by reusing Phase 1's `Game`/`PlayWindow`/`AssetManifest` renderer unmodified.

Nothing in `sim/game.py`, `sim/physics.py`, or the renderer changes — this phase only adds a new source of `Track` objects and a way to store/retrieve them.

- 2026-09-12 — Implemented all four Implementation-plan tasks (`neuroarena.sim.track_generation`, `neuroarena.tracks.{store,cli}`, plus the `tile_kind_for_open_edges` addition to `track.py`), 80 tests passing, clean `ruff`/`mypy --strict`. Three implementation-level findings surfaced, none changing a Requirement: (1) **The reference walk algorithm's length cap needed a Manhattan-distance feasibility prune**, not just a hard stop at `max_length` — the naive cap let the walk exhaust its step budget before backtracking toward closure, blowing up to ~150× more steps at larger sizes; the prune (an admissible lower-bound check: never extend past a cell from which closing back to start is already impossible within the remaining budget) fixed this without weakening the ±15% guarantee. (2) **A requested `size` whose ±15% window contains no even integer is mathematically unreachable, not merely hard** — a 90°-only closed loop always has an even tile count (the grid is bipartite by cell-coordinate parity, and every cycle in a bipartite graph has even length), so e.g. `size=5` (window `[5,5]`) can never close. Added a fast-fail guard that detects this up front and raises immediately with an explanatory message, instead of exhausting `max_attempts` on an impossible input. (3) **The generator originally let the loop's `start_cell` land on a curve tile** roughly 70% of the time; Phase 1's start/finish decor (an axis-aligned banner sized to the drivable width) was only ever validated against a straight-tile start and renders wrong on a curve. Fixed in the generator (prefer the first straight tile in the walked path for `start_cell`, falling back to the original behavior only at the 4-tile all-curve minimum), not the renderer, keeping Phase 1's renderer untouched per this phase's own constraint.
- 2026-09-12 — A whole-phase review (after all four tasks passed individually) found that the generator's length cap made every generated size land deterministically at the *top* of the ±15% window (e.g. `size=14` always produced 16; `size=120` always produced 138) rather than varying across it — in practice "size" meant "≈1.15× size". Escalated as a functionality decision rather than fixed unilaterally, per this project's standing rule that the user decides feature behavior. **Decided: spread results across the window** — each generation attempt now samples its own target length from the window's even integers (still fully deterministic per seed) — over the alternatives of leaving the bias undocumented-but-unchanged, or documenting it as accepted behavor, or flipping the bias to instead cluster at the window's bottom.
- 2026-09-12 — Recorded, not yet acted on: the same whole-phase review flagged several deferred-minor robustness gaps relevant to future phases — `tracks/store.py`'s manifest write is not atomic and a lost/corrupted `manifest.json` silently drops every prior track from enumeration (files remain on disk, findable by id, but not listed) with no rebuild-from-directory function yet; `load()` joins an unsanitized `track_id` into a filesystem path (not reachable today — nothing takes an arbitrary `track_id` yet — but becomes reachable once Phase 6 looks tracks up by id from SQLite); and `neuroarena.tracks` has no import-hygiene test of its own. None block this phase; flagged here so Phase 6's exploration pass inherits the context rather than rediscovering it.
- 2026-09-12 — One item remains open, not resolvable by an automated review: nobody has visually confirmed a generated track's rendered output (`--preview`) on an actual display — the arcade window is confirmed to open correctly (title/size/no crash) and generation's logical correctness is covered structurally (`Track.__post_init__` validates every generated track, including the `start_facing`-vs-open-edges check added this session, so a broken loop cannot exist as a `Track` object at all), but this project's own Phase 1 history shows headless/automated checks have missed real rendering bugs that surfaced within seconds of a human actually looking at and driving the result.
